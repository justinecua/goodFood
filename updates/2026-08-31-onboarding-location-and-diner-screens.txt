Onboarding (first launch only)

New OnboardingScreen.js - three paged slides (discover restaurants / rate
what you eat / find what's near you) on a horizontal FlatList with
pagingEnabled, dots, a Skip link and Next -> "Get Started". The visible
slide is tracked from the scroll offset in onMomentumScrollEnd rather than
onViewableItemsChanged; for three full-width pages that's simpler and has
no viewability config to get wrong.

utils/onboarding.js holds the flag (`hasSeenOnboarding` in AsyncStorage)
with hasSeenOnboarding() / markOnboardingSeen() / resetOnboarding(). Every
read and write is wrapped - a storage failure just means the slides show
again, which is the harmless direction to fail in. resetOnboarding() is
there for testing the first-run path without wiping app data.

SplashScreen now resolves the flag in the same Promise.all as the session
restore, so it costs no extra time, and replaces to Onboarding when unseen.
Finishing or skipping sets the flag and replaces to Login.


Location consent (every login)

New LocationPermissionScreen.js, matching the sketch: title "goodFood wants
to track your location", "Do you want to share your location?", two info
cards (stores your location / suggests restaurants near you), Allow and
Cancel.

useLoginForm resets to LocationPermission with `params.next` set to the
account's home route instead of resetting straight to the home screen; the
consent screen then resets to `next` on either button. Location is never a
gate - Cancel, a denied OS permission and a failed fix all continue to the
app, the last two after an alert explaining what won't work.

hooks/useLocationPermission.js does the actual work: PermissionsAndroid on
Android, Geolocation.requestAuthorization('whenInUse') on iOS, then one
getCurrentPosition wrapped in a promise, then saveUserLocation. It also
exports requestLocationPermission() on its own, which DinerMapScreen reuses
(it had its own near-identical copy).

api/services/location.js stores the coordinates under `userLocation` in
AsyncStorage as {latitude, longitude, capturedAt}. Device-only for now -
Account has no location FK and the `location` app has no views/urls, so
there is nothing to POST to yet. clearSession() clears it alongside the
session keys, since the coordinates belong to whoever was signed in.

The hardware back button is swallowed on this screen (BackHandler returning
true) - the user is already logged in by the time they see it, so back must
not drop them onto Login.

Android needed ACCESS_FINE_LOCATION / ACCESS_COARSE_LOCATION in the
manifest; only INTERNET was declared, which means the permission request in
the old DinerMapScreen could never have been granted. iOS already had
NSLocationWhenInUseUsageDescription.


Native crash: play-services-location

Pressing Allow (and opening the map) killed the app outright. It's a native
error, so the try/catch in the hook never sees it - the process just dies:

  FATAL EXCEPTION: mqt_v_native
  java.lang.IncompatibleClassChangeError: Found interface
    com.google.android.gms.location.FusedLocationProviderClient,
    but class was expected
      at com.agontuk.RNFusedLocation.FusedLocationProvider.getCurrentLocation
      at com.agontuk.RNFusedLocation.RNFusedLocationModule.getCurrentPosition

react-native-geolocation-service 5.3.1 (last released 2022) was compiled
against play-services-location 18.x, where FusedLocationProviderClient is
an abstract class. In 21.1.0 Google turned it into an interface.
react-native-maps asked for 21.3.0, Gradle resolves to the highest version
in the graph, and the old module then ran against a signature it wasn't
built for.

Fix: pin the last compatible release.
  - android/build.gradle ext: googlePlayServicesLocationVersion = "21.0.1"
    and googlePlayServicesVersion = "21.0.1" (the two names both libraries
    read via their safeExtGet helpers)
  - android/app/build.gradle: a resolutionStrategy.force on the same
    coordinate. The ext property alone is NOT enough - anything else
    requesting a higher version still wins without the force.

Verified with `./gradlew :app:dependencies --configuration
debugRuntimeClasspath | grep play-services-location` - 21.0.1 everywhere,
no upgrade arrows. The pin stays relevant after the maps swap below:
MapLibre reads the same googlePlayServicesLocationVersion ext, so both
agree.


react-native-maps -> MapLibre

The Google Maps key stopped working, so the map moved off Google entirely.
MapLibre needs no API key - it renders whatever vector style you point it
at. Added @maplibre/maplibre-react-native ^11.3.7, removed
react-native-maps, and dropped the now-dead com.google.android.geo.API_KEY
meta-data from the manifest. GOOGLE_MAPS_API_KEY is still in .env, unused.

Worth recording why the obvious alternatives don't work on Android:
  - OSM tiles via <UrlTile> inside react-native-maps still needs the key -
    the underlying view is the Google Maps SDK and it must authorize before
    it renders anything, even with mapType="none".
  - PROVIDER_DEFAULT / Apple Maps is key-free on iOS only; on Android the
    default provider IS Google.
  - Leaflet in a WebView is genuinely key-free but has worse gestures and
    perf, and OSM's public tile server usage policy rules it out for
    production traffic.

DinerMapScreen rewritten on the v11 API:
  MapView          -> Map, with mapStyle
  initialRegion    -> Camera initialViewState {center, zoom}
  animateToRegion  -> cameraRef.flyTo({center, zoom, duration})
  Marker coordinate-> Marker lngLat, with children (it's a view annotation,
                      so it renders our own dot + label)
  showsUserLocation-> <NativeUserLocation />

MapLibre works in [longitude, latitude] order, the opposite of the
{latitude, longitude} objects the rest of the app passes around.
getUserLocation() still returns the object form and the screen converts at
the boundary - worth remembering when restaurant pins get added.

constants/map.js holds the style URL and the default camera. Style is
OpenFreeMap's Liberty (https://tiles.openfreemap.org/styles/liberty):
OSM-based, free, no signup, no usage cap. Swap for MapTiler/Protomaps if an
SLA is ever needed. Default centre is Iligan at zoom 12 until the first fix
lands, then zoom 15.

The screen also keeps the previous behaviour of seeding from the stored
location before the live fix, and saving the fresh fix back. Added a
`cancelled` guard so a late fix can't setState after unmount. It got its
own DinerMapScreenStyle.js instead of borrowing ProfileScreenStyle plus
three inline {flex:1} objects.

iOS still needs `cd ios && pod install` - only Android was built here.


Emulator gotcha: this is not an API key problem

Most of the "the map is broken" time went here, so writing it down.

The Google symptom was:
  E Google Maps Android API: Error requesting API token. StatusCode=UNAVAILABLE
  W libbinder.Binder: ...maps.auth.IApiTokenService ... took 24041ms

UNAVAILABLE plus a 24-second binder timeout means Play Services never
reached Google to validate the key. A genuinely rejected key looks nothing
like this - it says "Authorization failure" and "Ensure that the Maps SDK
for Android is enabled" and dumps the key and SHA-1.

After the MapLibre swap the same underlying fault showed up as:
  MapLibre Native [ERROR] [Mbgl] [Setup]: loading style failed:
    Unable to resolve host "tiles.openfreemap.org"

The emulator could open raw TCP fine (nc -z to the tile server's IP:443 and
to 8.8.8.8:53 both succeeded) but could not resolve any hostname. Private
DNS was off. Launching with `-dns-server 8.8.8.8,8.8.4.4` did NOT help -
the emulator maps those to its internal forwarders 10.0.2.3/10.0.2.4, and
on the AndroidWifi interface in this system image that forwarding path is
broken (virtio-wifi bug).

What actually fixed it - drop the guest onto mobile data:
    adb shell svc wifi disable
    adb shell svc data enable
or launch the AVD with Wi-Fi off entirely:
    emulator -avd Pixel_9a -feature -Wifi

This is runtime state, not config, so it has to be redone after a wipe. If
maps look broken on a fresh emulator, check DNS before touching any keys.

Notes / follow-ups
- The diner screens have not been exercised on the device - reaching them
  needs a login. Verified through the bundle build and lint only.
- Whether MapLibre tiles actually paint is likewise unconfirmed; what was
  verified is that the two things that were failing (DNS, reaching the tile
  host) now work from inside the emulator.
- react-native-geolocation-service is unmaintained (2022, no New
  Architecture support) and only works here through the interop layer. The
  version pin unblocks it; migrating to
  @react-native-community/geolocation is the durable fix and is close to a
  drop-in - it would touch useLocationPermission.js and DinerMapScreen.js.
- The location is stored on the device only. Persisting it would need a
  location FK on Account (or a join table) plus an endpoint in the
  `location` app, which currently has a model and nothing else.
- DinerHomeScreen still shows a hardcoded address line ("Brgy. Poblacion,
  Quezon Avenue, Iligan ...") which is now visibly wrong given a real
  location is captured at login. Showing a street name needs reverse
  geocoding.
- The "See all" links on the home sections still have no handler; there are
  no list screens to point them at yet.
- Consent is asked on every login, not once - deliberate for now, but it
  should probably remember a previous "Allow" and skip straight through.
- The emulator ran on software GL ("Available Memory: 2830 MB, Required:
  5120 MB"), so MapLibre's vector rendering may feel sluggish there; that's
  a host-RAM issue, not the app.
