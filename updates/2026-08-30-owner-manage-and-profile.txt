Manage area split into its own screens

MyRestaurantScreen used to render the dish list, the category list and the
branch cards inline. It now shows the restaurant/location/hours/cuisine
cards plus a "Manage" card with three nav rows:

  Menu            -> MenuScreen           list of dishes
  Dish Categories -> DishCategoriesScreen list of categories
  Branches        -> BranchesScreen       list of branch locations

Each of those screens has a back button (new components/shared/
ScreenHeader.js - a chevron-left + centred title, used everywhere in the
manage section now) and keeps the bottom navbar. RestaurantBottomNavbar
gained a MENU_ROUTES list so the "Menu" tab stays highlighted on all of
them (MyRestaurant, Menu, DishCategories, Branches, AddDish,
AddDishCategory, RestaurantInformationScreen).

The Add buttons live on the list screens, not on MyRestaurantScreen:
MenuScreen has "Add Dish" + "Categories", BranchesScreen has "Add Branch".

OwnerListScreenStyle.js is shared by all three list screens (row layout,
thumbnails, the floating action bar).


Empty states

New components/shared/EmptyState.js (icon + title + message, plus a
`compact` variant). Used on:
  - MenuScreen / DishCategoriesScreen / BranchesScreen when the list is
    empty

    were showing hardcoded mock cards (Fish Tacos, fake rankings); those
    are gone, replaced with a compact empty state until the ranking
    endpoints exist
  - RestaurantNotificationScreen - "No notifications"
  - RestaurantInboxScreen - "No messages yet" (also removed a stray
    "Add Dish" button that had been left on this screen)


Operating hours: AM/PM

The hours inputs were 24-hour HH:MM, which is awkward on mobile. They're
now a 12-hour hour:minute field plus an AM/PM toggle per open/close time.
useRestaurantInfoForm.js keeps `opening_period` / `closing_period` in form
state and converts at the API boundary with to24h() / from24h() - the
backend TimeField still stores 24-hour, so nothing changed server-side.
Round-trip was checked: 12 AM -> 00:00, 12 PM -> 12:00, "1:5" -> 13:05.


Dish detail + edit/delete

- dish/queries.py getDish() - SELECT d.*, category name, plus the image
  rows ordered is_primary first. Route POST /api/get-dish/ {dish_id}.
- RestaurantDishDetailsScreen reworked: tapped from MenuScreen (rows are
  TouchableOpacity now), reloads on focus, shows all the dish fields, and
  has Delete + Edit buttons at the bottom.
- Edit reuses AddDishScreen. useAddDishForm(navigation, editing) takes the
  dish object; when editing it prefills every field (price as a string,
  the existing photo via mediaUrl), only uploads the photo if it's a fresh
  local pick, appends dish_id, and calls updateDish instead of addDish.
- updateDish() in dish/queries.py: UPDATE dish_dish ... WHERE dish_id;
  rowcount 0 -> "Dish not found"; a new photo flips the old primary image
  to is_primary = FALSE and inserts the new one as primary.
- deleteDish() - DELETE FROM dish_dish WHERE dish_id.
- Routes: POST /api/update-dish/ (multipart), /api/delete-dish/ {dish_id}.


Category edit/delete

- DishCategoriesScreen rows are tappable -> AddDishCategoryScreen with the
  category as a param. That screen is add-or-edit now: prefilled name +
  description, a "Delete category" link at the bottom when editing.
- updateDishCategory() / deleteDishCategory() in dish/queries.py, rowcount
  checked. Delete note: Dish.dish_category is ON DELETE SET NULL, so dishes
  in a deleted category just become uncategorised (no cascade).
- Routes: POST /api/update-dish-category/, /api/delete-dish-category/
  {dish_category_id}.


Branches moved off the restaurant info form

This is the bigger structural change. Branches used to be synced inside
addRestaurantInfo() - it deleted every branch for the restaurant and
reinserted from the form's branch cards. That can't coexist with a
per-branch edit/delete screen (saving the restaurant form would wipe any
branch added on its own screen).

So branches are now fully standalone:
  - removed the branch parsing + the delete-then-reinsert block from
    addRestaurantInfo(); removed the branch cards from
    RestaurantInformationScreen and all branch state/helpers/validation
    from useRestaurantInfoForm.js
  - new addBranch() / updateBranch() / deleteBranch() in
    restaurant/queries.py. addBranch resolves the restaurant from
    account_id (newest one) and errors with "Add your restaurant
    information first" if there isn't one. update/delete check rowcount.
  - Routes: POST /api/add-branch/ {account_id, branch_name, address,
    contact_number, latitude?, longitude?}, /api/update-branch/
    {branch_id, ...}, /api/delete-branch/ {branch_id}
  - new BranchFormScreen.js (add + edit + delete), reached from
    BranchesScreen ("Add Branch" button, or tap a row to edit)

getRestaurantInfo() still returns `branches` - BranchesScreen reads it for
the list.

Profile info screen: email + mobile, and the Cancel button

RestaurantProfileInformationScreen is used for two things: onboarding (from
RestaurantHome, sends name/gender/birthdate only) and profile editing (from
the profile menu). It now also shows Email and Mobile Number, prefilled
from the stored user.

Backend: addAdditionalInfo() SET clause gained
  email_address = COALESCE(NULLIF(%s, ''), email_address),
  mobile_number = COALESCE(NULLIF(%s, ''), mobile_number)
so an empty value never overwrites - onboarding, which doesn't send these,
is unaffected. Added an IntegrityError branch for the unique constraints
("That mobile number is already in use" / "That email is already in use").

validatorAdditionalInfo.js only checks email/mobile when those keys are in
the form (`'email' in form`), so the onboarding call still validates just
the three original fields.

Cancel button: it had no onPress at all, so it did nothing. Now
`navigation.goBack()`. Successful save also goBack()s instead of forcing a
jump to RestaurantHome.


New account endpoints

- POST /api/update-profile-photo/ (multipart {account_id, profile_image})
  -> updateProfilePhoto() - photo-only column update. Needed because
  addAdditionalInfo() would null out name/gender/birthdate if only a photo
  was sent.
- POST /api/change-password/ {account_id, current_password, new_password}
  -> changePassword() - SELECT the hash, check_password() the current one,
  make_password() the new one. Min 6 chars, checked server-side too.
- auth.js changePassword() reads account_id from the stored user blob (no
  token is attached to requests - see architecture notes).


Settings screen + theme scaffolding

RestaurantSettingsScreen: an "Appearance" card with Light / Dark rows, the
active one ticked. Persists the choice.

Scope note - this is scaffolding, not a themed app yet:

Seed data

`python manage.py seed_dishes` - adds ~6 Filipino dishes (Kare-Kare,
Crispy Pata, Sinigang na Hipon, Lumpiang Shanghai, Halo-Halo, Iced
Kalamansi) with their categories to the newest restaurant. Flags:
--account, --restaurant, --fresh. Idempotent by dish name (get_or_create).
Uses the ORM, not raw SQL, since it's a dev tool.
