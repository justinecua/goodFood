2026-08-30 — Add Restaurant Information

The owner can now add their restaurant: logo + cover images, the restaurant
details, and a location (city / province / region / country / lat / long).
The backend for this lives in its own restaurant app, written in the same
plain raw-SQL style as account/queries.py.

Backend

Two routes, mounted at /api/ through goodFoodProj/urls.py -> restaurant.urls:

  POST /api/get-restaurant-info/   { account_id }
       -> { restaurant: {...} | null, location: {...} | null }

  POST /api/add-restaurant-info/   (multipart/form-data)
       account_id, restaurant_name, restaurant_description, address,
       contact_number, email, city, province, region, country, latitude,
       longitude, restaurant_logo_img (file), restaurant_cover_img (file)
       -> { message } | { error }

getRestaurantInfo() reads the newest restaurant_restaurant row for the
account, then its location_location row, and returns both as plain dicts.

addRestaurantInfo() is create-or-update:
- validates account_id and the four NOT NULL columns (restaurant_name,
  address, contact_number, email)
- saves the logo/cover through Django storage and keeps only the path
- if the account already has a restaurant: update its location (or create
  one if it had none), then update the restaurant. COALESCE(%s, col) keeps
  the current image when no new file was sent.
- otherwise: insert the location, then the restaurant with created_at = NOW()
- a duplicate restaurant email hits the IntegrityError branch ->
  "That email is already used by another restaurant"

Style: it matches account/queries.py deliberately - one self-contained
function each, connection + cursor, inline SQL, dict(zip(...)) over
cursor.description, try / except IntegrityError / except / finally that
closes the cursor and connection, explicit commit(). An earlier version
with helper functions and column constants was reverted for being harder
to read.

views.py: GetRestaurantInfo and AddRestaurantInfo, both AllowAny.

These functions, views and routes briefly lived in the account app while
the feature was built, then moved here. account/queries.py, views.py and
urls.py are back to unchanged. checkInfoIfComplete stays in account - it
reports both personal and restaurant onboarding.


Frontend

RestaurantInformationScreen.js was a broken copy of the personal-info screen
(every input bound to form.lastname, a leftover gender dropdown and date
picker). Rewritten as three small module-scope components - TextField
(explicit label/value/onChangeText), LogoField (circular + camera badge),
CoverField (wide banner) - plus a chooseImage() helper. The body is a flat
list of <TextField>s in a ScrollView; Cancel goes back, Submit shows a
spinner.

useRestaurantInfoForm.js: a single FIELDS array drives the empty form, the
prefill, the submit body and the required-field check. On mount it calls
getRestaurantInfo() and fills the form + shows the saved logo/cover if a
restaurant exists (edit mode). Validates the four required fields and the
email format. Builds multipart FormData with account_id and all text
fields; only a freshly picked local image is uploaded. On success: alert,
then navigate to RestaurantHome.

home.js: getRestaurantInfo() and addRestaurantInfo(). The multipart POST
logic is now a shared postMultipart(path, formData) helper (explicit header,
20s timeout, clear error messages) that addAdditionalInfo() also uses.

AppNavigator registers the screen. The RestaurantHome "Add Restaurant
information" card now navigates to 'RestaurantInformationScreen' (it had the
wrong name before).


Testing (curl against the dev server)

Prettier clean on the changed frontend files.


Notes

  get-restaurant-info on its next mount and the home screen re-checks via
  check-info-complete
- restaurant / location still have no migration files but the tables exist
  in the DB with django_migrations records, so the raw SQL works. The real
  PK of restaurant_restaurant is `id`, not restaurant_id as the model says
  (see the 2026-08-30 backend-schema log).
- frontend/.env BACKEND_API_URL points at an old LAN IP; the dev machine's
  address changes between sessions. Set it and rebuild -
  react-native-config bakes .env at build time.
